# jev-mini

**Jev 的三个核心宣称，在你自己的 GPU 上跑一遍。**

[English](README.md)

```bash
python quickstart.py
```

一条命令，自动下载一个 0.5B 模型（~1GB，走 ModelScope，国内直连），
然后把「System One Model」的三个卖点逐条放到台面上验证。

在一块 **RTX 3060 Laptop（6GB，还开着浏览器）** 上跑完全程约 2 分钟。

---

## 这个仓库为什么存在

Jev 发布后被讨论得很热，但社区的质疑很具体：并行结构化输出不是新东西，
"0% 幻觉"偷换了 hallucination 的定义，而唯一真正重要的 calibration
**至今没有公开证据，也没有独立测试**。

那就自己测。本仓库不是 Jev 的复刻，而是一把**你能跑、能读、能改的尺子**：
用同一个本地模型、同一批问题，把"受限打分"和"自回归生成 JSON"放在一起比，
并且把大家都在谈、却没人量化的那个指标真正算出来。

**结论先放这里：前两个宣称是真的但被过度包装，第三个宣称比宣传中难得多。**

---

## 机制：一句话

> 不要让模型「写」出答案，让它给你允许的答案「打分」。

生成式模型回答选择题，要一个 token 一个 token 地把词拼出来。
这里一个 token 都不生成：把每个候选项接到 prompt 后面，读出模型赋予它的
对数概率，最高的就是决策，归一化后就是置信度。

三个结果随之而来，正好对应 TypeSafe 宣传的三件事：

| Jev 的说法 | 这里的实现 | 实测裁决 |
|---|---|---|
| Typed probabilistic decisions | 输出是 list 下标 | ✅ 成立 |
| Zero hallucinations | 结构上不可能越界 | ⚠️ 成立，但只是**类型**保证 |
| Calibrated confidence (RLCD) | 概率即返回值，可直接测 | ❌ 开箱很差，且**更大的模型校准一致地更差** |

第三行已在两个公开基准上做过交叉验证，并带 bootstrap 置信区间，
见[第 6 节](#6-在公开基准上的交叉验证)，不只依赖自建数据集。

## 实测数据

以下全部来自本机真实运行。

硬件：RTX 3060 Laptop 6GB · torch 2.9.1+cu126 · Python 3.14 · Windows
数据：**120 条客服工单 + 60 条评论**，人工标注，**标注先于任何模型运行**，
按 easy / medium / hard 分层。刻意放入歧义样本，因为
**只有在该犹豫的地方，校准才有意义**。

原始输出：[`results_0.5b.json`](results_0.5b.json) · [`results_1.5b.json`](results_1.5b.json)

### 1. 受限打分 vs 自回归生成 JSON

同样的权重、同样的问题，只有输出机制不同。

| | 受限打分 | 生成 JSON |
|---|---|---|
| 中位延迟（0.5B） | **126 ms** | 6389 ms |
| 中位延迟（1.5B） | **127 ms** | 3531 ms |
| 生成 token | **0** | 96 / 58 |
| 类型错误（0.5B） | **0 / 120** | 3 / 120 |
| 类型错误（1.5B） | **0 / 120** | 4 / 120 |

**0.5B 上快 50.8 倍，1.5B 上快 27.8 倍。** 提速全部来自砍掉解码，
不是模型变聪明了。

值得注意：1.5B 上受限打分**准确率反而更高**（0.550 vs 0.508）。
同样的权重、同样的问题——生成式路径损失了准确率，因为 token 花在了
复述格式而不是判断上。

### 2. 并行字段：K 个问题真的约等于 1 次前向吗

| 字段数 | 0.5B | 1.5B | 打分候选数 | 前向次数 |
|---|---|---|---|---|
| 1 | 128 ms | 135 ms | 5 | 2 |
| 8 | **126 ms** | **138 ms** | 26 | 2 |

**8 个字段的延迟是 1 个字段的 0.98x / 1.02x。** 在测量噪声范围内，
多问 7 个问题是免费的。这条宣称站得住：共享前缀只算一次，
KV cache 复用，所有候选项在一个 batch 里打分。

### 3. 校准：那个没有公开证据的指标

| 任务 | 模型 | 准确率 | 平均置信度 | ECE | 判断 |
|---|---|---|---|---|---|
| 工单分类 | 0.5B | 0.517 | 0.637 | 0.120 | 过度自信 |
| 是否紧急 | 0.5B | 0.608 | 0.594 | **0.084** | 基本诚实 |
| 情感分析 | 0.5B | 0.350 | 0.771 | **0.421** | 严重过度自信 |
| 工单分类 | 1.5B | 0.550 | 0.815 | **0.265** | 严重过度自信 |
| 是否紧急 | 1.5B | 0.725 | 0.927 | 0.208 | 严重过度自信 |
| 情感分析 | 1.5B | 0.433 | 0.757 | 0.324 | 严重过度自信 |

**最能说明问题的一行**：紧急度判断上，1.5B 把 **120 个样本中的 109 个**
放在 0.8 以上置信度，而该区间实际准确率只有 0.734。
它基本上只有一档：确信。

**反直觉发现：更大的模型准确率涨了，校准反而更差。**
紧急度上 0.5B 几乎是诚实的（ECE 0.084，甚至略微**欠**自信 −0.014），
而 1.5B 过度自信 +0.202。1.5B 的每一项任务都过度自信，0.5B 不是。
第 6 节显示这个发现只复现了一半——ECE 差距复现了，**方向没有**，
两个公开基准上都没有。

体现在运维上，阈值设 0.50 时：

| | 自动处理占比 | 放过的错误 |
|---|---|---|
| 0.5B | 78.3% | 32.5% |
| 1.5B | 96.7% | **43.3%** |

> 「模型更大，置信度更可信」——实测不支持。

难度分层也印证了这点：置信度几乎不跟随难度变化。0.5B 工单分类上，
easy 样本置信度 0.640，hard 样本 0.639，而准确率从 0.475 掉到 0.450。
**模型并不知道哪些题目更难。**

### 4. 温度标定：一个标量能挽回多少

| 模型 | 5 折拟合 T | 基线 ECE | 标定后（CV） | 标定后（单一切分） |
|---|---|---|---|---|
| 0.5B | 1.860 ± 0.190 | 0.128 | 0.085（−34%） | **0.030（−76%）** |
| 1.5B | 2.151 ± 0.161 | 0.311 | **0.089（−71%）** | 0.203（−35%） |

**两个模型都显著改善，且准确率在数学上完全不变**——温度无法移动 argmax。
一个标量，用几十条标注样本拟合，就让校准更差的那个模型 ECE 降了 71%。

这就是衡量 RLCD 的基准。如果一个宣称的校准优势能被"在留出集上拟合一个参数"
追平，它就不值一个新训练范式的名头。要真正下定论，需要 TypeSafe 公开数据。

> **本仓库的早期版本只有 18 条工单，当时测出温度标定让校准变得*更差*。**
> 那个结果是噪声：n=18 时单个样本翻转就能让 5 桶 ECE 移动好几个点。
> 数据扩到 n=120 后，结论翻转为稳定改善。这段历史保留在这里，
> 因为它是关于小样本校准结论的一个有用警告——**包括本 README 里的结论**。
> 第 6 节补上了这个警告的另一半：在 77 类和 150 类基准上，温度标定都完全失效。

### 5. 路由表：校准到底买到了什么（0.5B，工单分类）

| 阈值 | 自动处理占比 | 自动处理准确率 | 放过的错误 |
|---|---|---|---|
| ≥0.50 | 78.3% | 0.585 | 32.5% |
| ≥0.70 | 33.3% | 0.675 | 10.8% |
| ≥0.80 | 20.0% | 0.833 | 3.3% |
| ≥0.95 | 3.3% | **1.000** | **0%** |

这张表才是校准的实际用途：它是模型置信度和你的自动化策略之间的合同。

## 6. 在公开基准上的交叉验证

自建数据集有个结构性弱点：写标签的人同时也写了结论。所以同样的模型又在两个
本项目没有参与构建的标准基准上重跑了一遍，而且每个关键数字现在都带
bootstrap 置信区间——光给一个「0.057 对 0.097」，等于邀请读者做一个样本量
未必支撑得起的比较。

| | 类别数 | 随机基线 | 条数 |
|---|---|---|---|
| [banking77](https://arxiv.org/abs/2003.04807) | 77 | 1.3% | 3080（完整测试集） |
| [CLINC150](https://www.aclweb.org/anthology/D19-1131) | 150 | 0.67% | 1500 |

```bash
python scripts/cross_validate.py --dataset banking77 --model <路径> --per-class 40
python scripts/summarise.py          # 只读结果文件，不占 GPU
```

原始输出：[`b77_full_0.5b.json`](b77_full_0.5b.json) ·
[`b77_full_1.5b.json`](b77_full_1.5b.json) · [`clinc_0.5b.json`](clinc_0.5b.json)

### 核心结论现在有误差棒了

banking77 完整 3080 条测试集，2000 次 bootstrap 重采样：

| | 0.5B | 1.5B |
|---|---|---|
| 准确率 | 0.291 [0.276, 0.307] | **0.351** [0.334, 0.368] |
| ECE | **0.0573** [0.0435, 0.0731] | **0.0974** [0.0834, 0.1127] |
| 有符号偏差 | 欠自信 −0.047 | 欠自信 −0.097 |
| 中位延迟 | 272 ms | 477 ms |

**两个区间不重叠**（0.0731 < 0.0834）。更大的模型更准，且校准确实更差——
在此之前这只是一个点估计。之前用的 385 条抽样事后证明是可靠的
（0.294 / 0.0527 对 0.291 / 0.0573），但那个规模不足以确立这个结论。

### 误差方向随标签空间翻转，然后停住

有符号偏差 = 平均置信度 − 准确率，正值表示模型声称的把握超过它实际配得上的。

| 标签空间 | 数据集 | 0.5B 有符号偏差 | 方向 |
|---|---|---|---|
| 5 类 | 自建 | **+0.120** | 过度自信 |
| 77 类 | banking77 | **−0.047** | 欠自信 |
| 150 类 | CLINC150 | **−0.041** | 欠自信 |

CLINC150 上 0.5B 的准确率是 0.304，而随机基线只有 0.67%——46 倍，
所以这种犹豫并不是一个已经放弃作答的模型。

5 类到 77 类的翻转不是偶然——它在第三个数据集上复现了。但它**不会继续加深**：
150 类并不比 77 类更犹豫。驱动它的因素在 77 类以下某处就饱和了。

这把结论收窄到了有用的程度。它**不是**「小模型过度自信」，也**不是**
「类别越多越犹豫」，而是：**一个校准数字只属于它被测量的那个标签空间**。
这恰恰说明为什么厂商的校准数字不能被当作模型的固有属性来读。

运维上方向比幅度更重要。欠自信是更安全的失效方式：banking77 上阈值设 0.50 时，
0.5B 只放过 3.1% 的错误，而在 5 类数据集上是 32.5%。它拒绝了远超必要的工作量，
但它真正执行的那部分基本是对的。

### 温度标定不具普遍性

| 数据集 | 类别数 | 拟合 T | ECE 前 → 后 |
|---|---|---|---|
| 自建 | 5 | 1.860 | 0.128 → **0.085**（−34%） |
| banking77 | 77 | 1.121 | 0.0573 → 0.0866（**更差**） |
| CLINC150 | 150 | 1.362 | 0.0988 → 0.1355（**更差**） |

5 类上一个拟合标量挽回了大部分差距；在两个公开基准上它都让留出集 ECE 变差。
温度只能整体缩放一个分布，救不了排序本身不强、而离散程度已经差不多的模型。
**第 4 节那个 71% 的改善是那个数据集的性质，不是这个方法的性质**——
在读到任何「后处理已解决校准问题」的说法时，这一点值得记住。

### 这个差距是真的，还是分块造成的假象？

值得一问：两次运行的块大小都是按当时空闲显存自动决定的，而 fp16 下分块
确实会让单条置信度变化。同一个模型、同样 308 条，只改 `max_chunk`：

| max_chunk | 准确率 | ECE | 中位延迟 |
|---|---|---|---|
| 8 | 0.2922 | 0.045606 | 716 ms |
| 20 | 0.2922 | 0.045560 | 317 ms |
| 77（不分块） | 0.2922 | 0.045602 | 192 ms |

单条置信度最多变化 0.0043，但 **308 条预测没有一条改变标签**，
ECE 只动了 4.6e-05。这些扰动是无偏的，聚合时相互抵消而不是累积。
已发布的 0.040 差距大约是这个噪声地板的 **900 倍**，
所以它属于模型本身，而不属于显存分配器。

可以自己重跑：`python scripts/chunk_sensitivity.py <模型路径>`，
一旦这个抖动超过待验证差距的五分之一，脚本会直接报警。
原始数字见 [`chunk_sensitivity.json`](chunk_sensitivity.json)。

附带一个有用的结论：分得比需要的更细，会在答案完全相同的前提下
多花约 3 倍时间（耗时会随机器负载浮动，准确率和 ECE 两列不会）。
显存不紧张时，让它自动决定就好。

### 还缺什么

CLINC150 上的 1.5B。两次尝试都被操作系统中途杀掉：1.5B 模型上每条 150 个候选项，
超出了 16GB 内存 + 6GB 显卡能持续承受的范围，而且失败时会把整台机器拖住，
不是干净地报错。0.5B 那一列是完整的；150 类上的模型对比需要更大的机器，
这里选择留白，而不是用一次跑了一半的结果填上。

## 一个副产品发现：标签措辞会显著改变概率

同一个问题，只换 yes/no 的字面写法，极端正负样本之间的区分度差了近一倍：

| 标签 | 分离度 |
|---|---|
| `yes` / `no` | **+0.594** |
| `Yes` / `No` | +0.566 |
| `true` / `false` | +0.515 |
| `urgent` / `not urgent` | +0.316 |

如果你要把这类方法用到生产里，**标签措辞是一个需要调的超参**，
不是随手写的。

## 用法

```python
from jevmini import JevMini, Schema, Choice, Noul, Score

schema = Schema(fields=[
    Choice(name="category", options=["billing", "technical", "account"],
           question="Which department should handle this?"),
    Noul(name="urgent",   question="Is this urgent?"),
    Score(name="severity", low=1, high=5, question="How severe?"),
])

d = engine.decide("I was charged twice for order #4471.", schema)

d.value("category")       # 'billing' —— 一定是三个选项之一
d.confidence("category")  # 0.555
d["category"]["distribution"]
# {'billing': 0.555, 'account': 0.443, 'technical': 0.002}

if d.confidence("category") > 0.8:
    auto_route(d.value("category"))
else:
    escalate_to_human()
```

这个例子会走 escalate 分支：0.555 是 billing 和 account 之间的接近平局，
而一个校准过的数字的全部意义，就在于它会如实说出这一点，
而不是挑一个出来、装作很确定。

`Score` 除了 argmax 还返回**期望值**：一条在 2 星和 4 星之间摇摆的评论
应该读作 3，而不是险胜的那个桶。

## 安装

```bash
git clone https://github.com/RichardoMrMu/jev-mini
cd jev-mini
python -m venv .venv && .venv\Scripts\activate   # Linux/macOS: source .venv/bin/activate

pip install torch --index-url https://download.pytorch.org/whl/cu126

```

**国内网络**：模型走 ModelScope，不需要 HuggingFace 访问。
pip 可加 `-i https://pypi.tuna.tsinghua.edu.cn/simple`。

**完整报告**：

```bash
python scripts/benchmark.py --model <本地模型路径> --out results.json
```

### 显存很小或内存吃紧

本仓库就是在这种环境下开发的（6GB 显卡 + 桌面已占约 2GB + 16GB 内存）。
`quickstart.py` 已默认设置 `TRANSFORMERS_NO_CACHING_ALLOCATOR_WARMUP=1`，
避免 transformers 按整模型大小预留显存——在共享显卡上，
即使权重本身放得下，这个预留也会失败。

候选项是分块打分的，块大小按空闲显存自动决定，所以标签空间再大也不会撑爆内存；
给 `JevMini` 传 `max_chunk=N` 可以固定它。

实测峰值显存：自建数据集上 **0.5B → 1569 MB，1.5B → 3582 MB**；
banking77 上 **1858 MB / 3409 MB**（77 个候选项同时在飞）。

若遇到 `OSError 1455 页面文件太小`，那是系统提交内存耗尽而非显存问题。
关掉 WSL（`wsl --shutdown`）或其他大内存进程即可。

还有一个更硬的限制，规划跑批前值得知道：**CLINC150 上的 1.5B 在这台机器上
被系统杀了两次。** 1.5B 模型每条 150 个候选项，超出了 16GB 内存能持续承受的范围，
而且它会把整台机器拖住，不是干净地报错。先用小的 `--per-class` 起步，
摸清吞吐后再放大。

## 这个仓库**没有**证明什么

必须说清楚，否则就是在用另一种方式夸大：

- **这不是 Jev。** 它的权重、架构、参数量都没公开。这里用的是通用小模型 +
  受限打分。所有数字只描述**本方法在本机**的表现。
- **不能用来反驳 TypeSafe 的数字。** 他们的 193x / 444x 是特定工作流下的
  最大差距；这里的 27.8–50.8x 是另一组任务、另一个模型、另一块卡。
- **自建数据集不大。** 120 + 60 条，够做难度分层，仅此而已。
  公开基准要大得多——banking77 完整 3080 条测试集、CLINC150 的 1500 条——
  带 bootstrap 置信区间的是这批数字。凡是区间缺失或由重建得来的，
  结果文件里都写明了。
- **校准结论依赖标签空间。** 过度/欠自信的方向在 5 类和 77 类之间翻转，
  并在 150 类上稳住。不管你从这里得出什么结论，换一个标签空间都要重新测。
- **对照表里缺一格。** CLINC150 上的 1.5B 没能在这台机器上跑完，
  所以 150 类下的模型规模对比仍然是开放的。
- **没有实现 RLCD。** 它的训练方法和 reward function 都未公开，无法复现。
  这里提供的是**测量它的工具**。

能证明的是：受限打分带来的类型安全和并行加速是真实且易得的。
而校准——真正难的那部分——在一个没有专门优化过的模型上确实很差，
并且**把模型换大只会更差，不会更好**：banking77 完整测试集上，
0.5B 和 1.5B 的 95% 置信区间不重叠。至于拟合一个温度，
它并不是从单个数据集看上去的那种普适解药：5 类上挽回了 71%，
两个公开基准上都让结果变差。

```
quickstart.py      一键体验
```

代码有详细注释，尤其是三个值得知道的坑。
**为什么只对标签 token 打分**——把问题 stem 也算进去会把分布压平，
这是开发中真实踩到的 bug：修复前 billing 只有 0.298，修复后 0.555，
而第二名 account 是 0.443——修复做到的是把第一名从接近平局中分出来，
不是凭空制造确定性。
**为什么必须做长度归一化。** 以及**为什么要分块打分**——
77 个选项 × 15 万词表是 1GB 的 logits，会让 6GB 显卡直接 OOM；
分块把峰值显存从 3548 MB 降到 1234 MB。
改变分块大小会让概率在 fp16 下最多抖动约 0.004——如果你要比较两次用了不同
块大小的运行，这个量级是会影响判断的，所以这种场景下请固定 `max_chunk`。
它是归约顺序而非 cache bug：误差不随块序号增长，同样的对比在 fp32 下
降到 3e-6。
